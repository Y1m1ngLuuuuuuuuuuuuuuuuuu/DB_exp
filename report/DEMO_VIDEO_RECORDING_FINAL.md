# 学生选课成绩管理系统录屏最终版脚本

## 录制定位

视频建议控制在 8 到 10 分钟。展示重点不是单纯浏览页面，而是说明系统如何把数据库原理2中的设计流程、ER 建模、关系模型、规范化、完整性约束、触发器、事务、锁、视图和运行维护落实到一个学生选课成绩管理系统中。

录屏过程中只展示页面、报告、测试输出和必要 SQL 片段，不展示明文密码文件，不现场修改数据库结构，不把后续扩展讲成已实现。

## 演示前准备

1. 启动 openGauss 容器，并确认数据库已经完成初始化、完整性增强和绩点规则脚本。
2. 启动 Streamlit：

```bash
.venv/bin/streamlit run app.py --server.port 8501 --server.address 127.0.0.1
```

3. 准备最终 PDF 报告。
4. 准备演示账号：管理员使用 `A001`，教师可使用 `T005` 或 `T021`，学生可使用 `20240004`、`20240008` 或 `20240012`。
5. 明文密码只从本地凭据文件中查看，录屏画面不展示该文件。

边界选课测试建议使用以下学生账号：

| 账号 | 适合展示的场景 | 操作对象 | 预期结果 |

| `20240011` | 仅剩一名、先修课未满足、已满课程 | `EDGE_ONE_LEFT` / `9002`；`EDGE_ADV` / `9007`；`EDGE_FULL` / `9001` | `9002` 选课成功；`9007` 因先修未满足失败；`9001` 因容量已满失败 |

## 详细操作顺序

### 1. 登录与角色体系

1. 打开系统登录页。
2. 指出账号规则：学生使用学号，教师使用教师编号，管理员使用管理员编号。
3. 输入管理员账号 `A001` 登录。

讲解句：

> 系统没有把所有用户信息混在一张表中，而是用 `user_account` 保存认证信息，再用 `student`、`teacher`、`admin_profile` 保存不同角色档案。数据库触发器负责检查账号角色和档案类型是否一致。

### 2. 管理员首页与数据规模

1. 展示管理员首页指标卡。
2. 指出学生、教师、课程、教学班、选课记录和审计日志数量。

讲解句：

> 这些统计结果来自基础表和视图，说明系统已经不是少量样例数据，而是有一定规模的演示数据，可以支撑查询、统计和审计展示。

### 3. ER 图和逻辑模型

1. 切换到 PDF 报告。
2. 展示概念 ER 图。
3. 展示逻辑关系模型或第 4 章关系模式定义。

讲解句：

> 概念设计阶段关注实体和联系，逻辑设计阶段把它们转换成关系模式。学生和教学班之间的多对多关系通过 `enrollment` 转换；课程和先修课程之间的自关联通过 `course_prerequisite` 转换。

### 4. 课程、教学班和时间片

1. 在管理员端展示课程或教学班管理页面。
2. 指出课程、教师、学期、教室、容量、上课时间。

讲解句：

> 课程定义与教学班分离可以避免课程名称、学分、教师、教室和学期信息在同一张大表中重复出现。上课时间用 `course_schedule` 结构化保存，便于数据库执行时间冲突检查。

### 5. 学生选课

1. 退出管理员账号，登录学生账号。
2. 打开课程查询与选课页面。
3. 筛选开放学期，选择一门有余量、无冲突的课程。
4. 点击选课并展示成功提示。
5. 打开课表确认课程出现。

讲解句：

> 选课写入不是简单 INSERT，而是由服务层事务调用数据库函数。数据库层锁定目标教学班，统计已选人数，并通过触发器检查容量、时间冲突、先修课程和同课跨班限制。

### 6. 选课边界与错误案例

建议录制时按“一个成功案例 + 两到三个失败案例”的节奏展示，既能说明系统可用，也能突出数据库层完整性约束。

#### 案例 A：仅剩一名课程成功

1. 登录学生账号 `20240011`。
2. 进入课程查询与选课页面。
3. 搜索 `EDGE_ONE_LEFT` 或课程名“演示：仅剩一名课程”。
4. 选择教学班 `9002`。
5. 页面应提示选课成功，课程剩余容量由 1 变为 0。

讲解句：

> 这个案例用于展示正常选课路径。`EDGE_ONE_LEFT` 在测试数据中只剩 1 个名额，学生 `20240011` 选课时，数据库函数会锁定目标教学班，再统计 `enrollment` 中的已选人数。系统没有维护 `selected_count` 基础字段，而是在事务内通过聚合统计和行级锁保证容量一致。

#### 案例 B：已满课程失败

1. 登录学生账号 `20240009`，也可以继续使用 `20240011`。
2. 搜索 `EDGE_FULL` 或课程名“演示：已满课程”。
3. 选择教学班 `9001`。
4. 页面应提示容量已满，选课失败。

讲解句：

> `EDGE_FULL` 的容量是 8，测试数据已经预置 8 条 `selected` 选课记录。触发器在写入前重新统计当前已选人数，发现已选人数已经达到 `max_capacity`，因此拒绝插入。这说明容量检查最终由数据库层兜底，而不是只依赖页面显示的剩余名额。

#### 案例 C：时间冲突失败

1. 登录学生账号 `20240009`。
2. 该学生已经选中 `EDGE_CONFLICT_A` / `9003`。
3. 搜索 `EDGE_CONFLICT_B` 或课程名“演示：时间冲突待选课”。
4. 尝试选择教学班 `9004`。
5. 页面应提示时间冲突，选课失败。

讲解句：

> `9003` 和 `9004` 都安排在周六第 1--2 节。系统把上课时间拆成 `course_schedule` 中的 `weekday`、`start_section` 和 `end_section`，触发器可以用结构化字段判断时间区间是否重叠。这是 1NF 设计服务业务规则的典型例子。

#### 案例 D：同课跨班失败

1. 登录学生账号 `20240010`。
2. 该学生已经选中 `EDGE_SAME` 的教学班 `9005`。
3. 搜索 `EDGE_SAME` 或课程名“演示：同课跨班限制”。
4. 尝试选择同课程的另一个教学班 `9006`。
5. 页面应提示同一学期同一课程不能重复选择不同教学班。

讲解句：

> `UNIQUE(student_id, offering_id)` 只能防止重复选择同一个教学班，不能表达“同一学生同一学期同一课程只能选一个教学班”。这个规则需要跨 `enrollment` 和 `course_offering` 查询课程号与学期，因此由 `trg_enrollment_guard` 触发器完成。

#### 案例 E：先修课程未满足失败

1. 登录学生账号 `20240011`。
2. 搜索 `EDGE_ADV` 或课程名“演示：先修未满足课程”。
3. 尝试选择教学班 `9007`。
4. 页面应提示先修课程条件不满足。

讲解句：

> `EDGE_ADV` 依赖先修课程 `EDGE_PRE`。触发器会检查学生是否存在对应先修课程的 `completed` 选课记录，并且最终成绩是否达到 60 分。学生 `20240011` 没有通过该先修课程，因此数据库拒绝选课。

边界案例收束讲解：

> 这些成功或失败结果都不是单靠前端判断，而是由数据库函数、唯一约束和触发器共同维护。即使绕过 Streamlit 页面直接写数据库，容量、时间冲突、同课跨班和先修课程规则仍然会被数据库层检查。

### 7. 学生成绩与绩点

1. 打开学生成绩页面。
2. 展示课程、学分、成绩、状态和绩点。

讲解句：

> 系统不在 `enrollment` 中保存 `gpa_point` 派生字段，而是通过绩点规则表和视图计算。这样成绩变化或绩点规则变化时，不会出现基础表中成绩和绩点不一致的问题。

### 8. 教师成绩录入与审计

1. 登录教师账号。
2. 打开教学班或成绩录入页面。
3. 选择一个学生，修改成绩并填写原因。
4. 保存后展示成功提示。

讲解句：

> 成绩更新和审计日志写入处于同一事务中。服务层设置当前操作者，数据库触发器写入 `score_change_log`。如果日志写入失败，成绩更新也会回滚。

### 9. 管理员审计日志

1. 回到管理员账号。
2. 打开成绩审计日志页面。
3. 展示旧成绩、新成绩、修改人、修改时间和原因。

讲解句：

> 审计日志不是普通冗余字段，而是独立事件记录。它保留了成绩修改历史，支持后续追责和运行维护。

### 10. 并发抢课测试

1. 展示并发测试脚本输出或报告附录。
2. 重点展示：

```text
success_count = 1
failed_count = 1
selected_count_in_db = 1
```

讲解句：

> 两个数据库连接同时抢一个容量为 1 的教学班，最终只有一个成功。核心原因是 `SELECT ... FOR UPDATE` 对同一个教学班行加锁，使容量检查和写入按事务顺序执行。

## 收尾总结

可以用下面这段作为结尾：

> 总体来看，本系统把选课业务建模为一个规范化的关系数据库应用。报告从规划、需求、概念、逻辑、规范化、完整性、事务锁、物理设计到运行维护展开，重点体现数据库原理2中的 ER 模型、关系模型、范式、触发器、事务、锁、索引和视图。后续可以继续完善生产级权限、备份恢复、运行监控、教师评价和更大规模并发压测。
