\chapter{逻辑结构设计}

\section{从 ER 模型到关系模式}

逻辑结构设计的任务是把概念结构设计中的实体、属性和联系转换为关系数据库可以直接实现的关系模式。系统采用关系模型表达数据结构：实体转换为基本关系，一对多联系通常通过在多端保存外键实现，多对多联系转换为独立中间关系，多值属性转换为独立关系，自关联联系通过同一实体表的两个外键表达。

第 4 章采用“分模块关系模式定义 + 主键、候选键与外键约束汇总 + 多对多转换说明”的方式描述逻辑结构。正文不再使用完整字段列表大表作为主要表达，以避免字段名在窄列中被强行断行。

\section{关系模式定义}

根据概念结构设计结果，系统将实体及联系转换为关系模式。为便于说明，以下按照组织结构、账户与角色、课程教学、选课成绩四类模块列出核心关系模式。下划线字段表示主键，标注 UK 的字段表示候选键或唯一约束，箭头表示外键引用关系。

主键用于保证实体完整性。系统中学生、教师、课程等业务实体使用稳定业务编号作为主键；会话、教学班、选课记录、日志和绩点规则等记录型数据使用代理主键，便于自动生成和长期维护。候选键和唯一约束用于表达业务唯一性，例如登录账号唯一、账号与角色档案一对一、同一学生不能重复选择同一教学班、同一教学班不能重复登记同一时间片等。

\section{外键与参照完整性}

外键用于表达关系模式之间的参照完整性。组织结构中，专业引用院系；人员档案中，学生、教师和管理员档案引用统一账号；课程教学中，教学班引用课程、学期、教师和教室；选课成绩中，选课记录引用学生和教学班，成绩审计日志引用选课记录和操作账号。

这些外键保证了“不能为不存在的学生选课”“不能为不存在的教学班登记时间片”“不能记录不存在选课记录的成绩修改”“学期不能引用不存在的绩点规则”等基本规则。角色类型一致性、教学班容量不超过教室容量、先修课程环路和选课时间冲突属于跨表业务规则，普通外键不能完整表达，系统通过触发器进一步维护。

\section{多对多关系和自关联关系转换}

学生与教学班之间是典型多对多关系：一个学生可以选择多个教学班，一个教学班也可以被多个学生选择。若直接在学生表中保存课程列表，或在教学班表中保存学生列表，都会产生非原子属性并破坏第一范式。因此逻辑设计使用 \code{enrollment} 作为中间关系，把多对多关系转换为两个一对多关系：

\begin{itemize}
  \item \code{student} 与 \code{enrollment} 构成 1:N，一名学生可以对应多条选课记录；
  \item \code{course_offering} 与 \code{enrollment} 构成 1:N，一个教学班可以对应多条选课记录。
\end{itemize}

\code{enrollment} 不只是连接表，也保存联系属性。\code{select_time} 表示选课时间，\code{status} 表示选课状态，\code{final_score} 表示该学生在该教学班中的最终成绩，\code{remark} 保存备注。\code{UNIQUE(student_id, offering_id)} 防止重复选择同一教学班，同课跨班限制由选课完整性触发器进一步保证。

课程与先修课程之间存在自关联。一门课程可以有多门先修课程，一门课程也可以作为多门课程的先修课。系统使用 \code{course_prerequisite(course_id, prereq_course_id)} 表达该自关联，其中两个字段都引用 \code{course.course_id}，复合主键保证同一先修关系不会重复登记，检查约束和触发器用于防止自指与环路。

\section{课程定义、教学班与时间片}

\code{course} 与 \code{course_offering} 的分离是逻辑设计中的关键点。\code{course} 保存课程定义，例如课程名称、课程类型、学分、总学时和所属学院；\code{course_offering} 保存某课程在某学期、由某教师、在某教室开设的具体教学班。这样，同一课程在不同学期或不同教师下开班时，不需要重复保存课程名称、学分和学时，减少了更新异常。

\code{course_schedule} 用于表达教学班的多值时间属性。一个教学班可以有多个上课时间片，因此逻辑设计将时间片独立成表，每行保存 \code{weekday}、\code{start_section} 和 \code{end_section}。该设计使数据库能够直接按星期和节次进行时间冲突检查，而不是依赖应用层解析展示文本。
